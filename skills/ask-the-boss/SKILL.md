# ask-the-boss

Slack 経由でユーザーの上司に質問を投げ、返信が来るまで待って回答を受け取るためのスキル。
バックエンドはこのリポジトリの Go 製 CLI `ask-the-boss` を使う。

## いつ使うか

- 本番環境への反映、データ削除、課金が発生する操作など **後戻りしにくい判断** の承認がほしいとき
- 仕様・優先順位・トレードオフの **最終判断** を人間に委ねたいとき
- ユーザーから **「上司に確認して」「承認を取って」** と明示的に依頼されたとき

逆に、AI が自分で判断してよい些細なことや、ユーザー本人にその場で聞けば済むことには使わない
(その場合はユーザーに直接質問する)。

## 前提条件

### 1. 環境変数（4つ）

CLI は以下の環境変数を必要とする。シェルのプロファイルや direnv、Claude Code の env 設定などで
あらかじめ設定されている想定。ローカル開発中のみ、リポジトリ直下に `.env` があれば読み込んでよい。

| 変数 | 用途 |
|---|---|
| `SLACK_WEBHOOK_URL` | 質問の投稿先（Incoming Webhook）|
| `SLACK_BOT_TOKEN` | 返信の読み取り（要 `channels:history` 等 + `users:read`）|
| `SLACK_CHANNEL_ID` | Webhook の投稿先チャンネル ID |
| `SLACK_BOSS_USER_ID` | 上司の Slack ユーザー ID（メンション & 返信判定）|

未設定ならユーザーに設定を依頼する（勝手に値を推測しない）。

### 2. バイナリ `ask-the-boss`

次の優先順で用意する:

1. すでに PATH 上にあればそれを使う（`command -v ask-the-boss`）。
2. 無ければ `go install github.com/udzura/ask-the-boss@latest` で導入する
   （`$(go env GOPATH)/bin` に入る。PATH に含める）。
3. プラグインとして導入済みの場合、`${CLAUDE_PLUGIN_ROOT}` に Go ソースがあるので
   `go build -o "${CLAUDE_PLUGIN_ROOT}/ask-the-boss" "${CLAUDE_PLUGIN_ROOT}"` でビルドしてもよい。
4. このリポジトリ内で作業しているなら `go build -o ask-the-boss .` でビルドする。

## 使い方の手順

### Step 1: 質問を組み立てる

**背景（`--background`）と質問内容（`--question`）を必ず分ける。** 上司が短時間で判断できるよう、
背景は「今どういう状況か・なぜ聞くのか」、質問は「YES/NO や選択肢など、答えてほしいこと」を簡潔に書く。

- 良い質問: 判断に必要な情報が背景に揃っていて、質問文で答えの形式が明確
- 悪い質問: 背景が無く「これやっていいですか？」だけ / 長すぎて要点が不明

長文になる場合は一時ファイルに書いて `--question-file` / `--background-file` で渡してもよい。

**質問者（=ユーザー本人）の名前は原則 `--from "名前"` で明示する。** 上司は「誰からの質問か」が
分かった方が判断・返信しやすい。ユーザーの名前が分かっていればそれを渡し、分からなければ
「どのお名前で質問しますか？」と一度確認する。受け取った文字列はそのまま表示される。

ただし **ユーザーが「名前を出さないで」「匿名で聞いて」等と指示した場合は `--from` を付けない**
（省略すると質問者表記は出ない）。名前を出すかどうかは最終的にユーザーの意向を優先すること。

### Step 2: CLI を実行して回答を待つ

上司の返信には時間がかかることがある。**バックグラウンド実行して定期的に出力を確認する**のが安全
（Bash ツールの実行上限より長く待てる）。`--timeout` は状況に応じて設定する（既定 30m）。

```bash
# ローカル開発時のみ、リポジトリ直下に .env があれば読み込む
[ -f ./.env ] && { set -a; . ./.env; set +a; }

ask-the-boss ask \
  --from "山田太郎" \
  --background "PR #123 のレビューが完了し、CI もグリーンです。本番デプロイの準備が整いました。" \
  --question "この変更を本番に反映してよいですか？（はい／いいえ／保留 でお答えください）" \
  --timeout 30m --interval 15s
```

- 標準エラーに `質問を投稿しました (id=...)。上司の返信を待っています...` が出れば投稿成功。
- コマンドが正常終了（exit 0）すると、**標準出力に上司の回答テキスト**が 1 つ出力される。
  回答内のメンションは表示名（`@名前`）に解決済み。

Claude Code での実行時は `run_in_background: true` で起動し、出力ファイルを数十秒間隔で
確認する。完了通知（exit 0）が来たら出力ファイルを読んで回答を取得する。

### Step 3: 回答を反映する

- 得られた回答を要約せず正確にユーザーへ共有し、その指示に従って作業を続ける。
- **承認が得られた場合のみ**、当該の後戻りしにくい操作を実行する。
- 否認・保留・条件付きなら、その内容に従って中断・調整する。勝手に承認と解釈しない。

## エラー時の対処

| 症状 | 原因と対処 |
|---|---|
| `webhook への投稿に失敗しました` | `SLACK_WEBHOOK_URL` が誤り/失効。ユーザーに再発行を依頼。 |
| `conversations.history が失敗しました: not_in_channel` | Bot が対象チャンネル未参加。`/invite @Bot` を依頼。 |
| `... : missing_scope` / `invalid_auth` | Bot トークンのスコープ不足/失効。`channels:history`・`users:read` 等を確認。 |
| `タイムアウトしました` | 時間内に上司の返信なし。`--timeout` を延ばすか、ユーザーに相談。 |

## 注意

- このスキルは **人間の判断を代行しない**。回答を捏造したり、返信を待たずに承認済みとして
  進めたりしてはならない。返信が無いままなら「まだ回答待ち」であることを正直に伝える。
- 質問は上司の Slack に実際に届く。連投・無意味な質問を避け、1 回で判断できる質問にまとめる。
