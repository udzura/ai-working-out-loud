# wol-slack

作業しながらその内容を Slack に共有し続ける（Working Out Loud）ためのスキル。
バックエンドはこのリポジトリの Go 製 CLI `wol-slack` を使い、Incoming Webhook で投稿するだけ
（返信は待たない）。ask-the-boss と違って**承認を求めるものではなく、一方向の共有**である。

## いつ使うか

- ユーザーが **「WOL を始めて」「作業ログを Slack に流して」「N 分ごとに進捗を共有して」** と依頼したとき
  → Step 1 で間隔を確認し、継続モードに入る
- 継続モード中に **決めた間隔が経過した** とき → Step 4 で投稿
- **「WOL して」「今の進捗を共有して」「さっきからの分をまとめて」** と促されたとき
  → 間隔の経過を待たずに Step 5 で即投稿
- **「WOL 止めて」「もう共有しなくていい」** と言われたとき → Step 6 で停止

使わない場面: 上司の判断・承認が必要なとき（それは `ask-the-boss` スキルの仕事）。
また、まだ何も進捗が無いとき（投稿すべき差分が無いなら投稿しない）。

## 前提条件

### 1. 環境変数（1つ）

| 変数 | 用途 |
|---|---|
| `WOL_SLACK_WEBHOOK_URL` | 投稿先の Incoming Webhook URL（優先）|
| `SLACK_WEBHOOK_URL` | 上記が無い場合に使用（ask-the-boss と同じチャンネルに投げる場合）|

どちらも未設定ならユーザーに設定を依頼する（勝手に値を推測しない）。
ローカル開発中のみ、リポジトリ直下に `.env` があれば読み込んでよい。

### 2. バイナリ `wol-slack`

次の優先順で用意する:

1. すでに PATH 上にあればそれを使う（`command -v wol-slack`）。
2. 無ければ `go install github.com/udzura/ai-working-out-loud/cmd/wol-slack@latest` で導入する
   （`$(go env GOPATH)/bin` に入る。PATH に含める）。
3. プラグインとして導入済みの場合は
   `go build -o "${CLAUDE_PLUGIN_ROOT}/wol-slack" "${CLAUDE_PLUGIN_ROOT}/cmd/wol-slack"` でもよい。

## 状態ファイル

継続モードの設定と、前回投稿以降の作業ログをここに持つ。コンテキストが圧縮されても続けられる
ように、**会話の記憶だけに頼らず必ずファイルに書く**。

- パス: `${WOL_SLACK_STATE_FILE:-${XDG_STATE_HOME:-$HOME/.local/state}/wol-slack/<プロジェクトのディレクトリ名>.md}`
- 秘匿情報（トークン・Webhook URL）は書かない。

形式（`---` より下が前回投稿以降の作業ログ）:

```
interval_minutes: 30
from: 山田太郎
last_posted_epoch: 1755600000
---
- 14:05 wol-slack CLI の実装に着手
- 14:20 テストを追加してグリーン
```

## 使い方の手順

### Step 1: 開始時に投稿間隔を確認する

継続モードに入る前に、**必ず一度ユーザーに間隔を確認する**（勝手に決めない）。

> 何分ごとに WOL を投稿しますか？（例: 15分 / 30分 / 60分。「都度促されたときだけ」も可）

あわせて、投稿者名を `--from` に載せたいかも確認する（名前が分からなければ聞く。「名前は出さないで」
と言われたら `--from` を付けない）。決まったら状態ファイルを作成する。

```bash
STATE="${WOL_SLACK_STATE_FILE:-${XDG_STATE_HOME:-$HOME/.local/state}/wol-slack/$(basename "$PWD").md}"
mkdir -p "$(dirname "$STATE")"
cat > "$STATE" <<EOF
interval_minutes: 30
from: 山田太郎
last_posted_epoch: $(date +%s)
---
EOF
```

開始した旨と、次の投稿見込み・停止方法（「WOL 止めて」と言えばよい）をユーザーに一言伝える。
「都度促されたときだけ」を選ばれた場合は `interval_minutes: 0` とし、Step 4 の時間判定はしない。

### Step 2: 作業ログを溜める

作業の区切り（実装・調査・テスト・修正などが一段落するたび）に、状態ファイルの `---` 以下へ
**1行ずつ追記**する。これが次の投稿の材料になる。

```bash
echo "- $(date +%H:%M) テストを追加し go test をグリーンにした" >> "$STATE"
```

書くのは事実の要約（何をしたか・結果どうなったか）。ファイル名や PR 番号など具体を1つ入れると
読み手が追いやすい。秘匿情報やトークンは書かない。

### Step 3: 投稿すべきか判定する

**応答を返す前（作業が一段落したタイミング）に毎回**、経過時間を確認する。

```bash
NOW=$(date +%s)
LAST=$(grep '^last_posted_epoch:' "$STATE" | cut -d' ' -f2)
INTERVAL=$(grep '^interval_minutes:' "$STATE" | cut -d' ' -f2)
[ "$INTERVAL" -gt 0 ] && [ $(( (NOW - LAST) / 60 )) -ge "$INTERVAL" ] && echo POST_NOW
```

`POST_NOW` が出て、かつ `---` 以下にログが1行以上あれば Step 4 に進む。ログが空なら投稿せず、
`last_posted_epoch` も更新しない（無内容な投稿を避ける）。

### Step 4: 投稿する

`---` 以下のログを、そのまま貼るのではなく**読み手向けに整えてから**投稿する。3〜6行程度で、
「やったこと」「今どうなっているか」「次にやること」が分かる形にする。

```bash
[ -f ./.env ] && { set -a; . ./.env; set +a; }

wol-slack --title "パフォーマンス調査" --from "山田太郎" --summary "$(cat <<'EOF'
- N+1 クエリを 3 箇所修正（app/models/user.rb ほか）
- ベンチマークでレイテンシが 40% 改善、テストはグリーン
- 次: キャッシュ層の TTL 設定を見直す
EOF
)"
```

- 見出し `--title` には今取り組んでいるテーマを入れる（省略可）。
- 投稿は一方向で返信を待たないため、`run_in_background` は不要。数秒で終わる。
- 標準エラーに `作業まとめを投稿しました` が出て exit 0 なら成功。
- 本文を確認したいだけなら `--dry-run` で投稿せず組み立て結果を表示できる。

投稿に成功したら、状態ファイルの `last_posted_epoch` を今の時刻に更新し、`---` 以下のログを
**クリアする**（次の投稿は必ず「前回投稿以降の差分」になる）。

```bash
NOW=$(date +%s)
sed -i.bak "s/^last_posted_epoch:.*/last_posted_epoch: $NOW/" "$STATE"
sed -i.bak '/^---$/,$d' "$STATE" && echo '---' >> "$STATE" && rm -f "$STATE.bak"
```

投稿したことはユーザーにも一言伝える（投稿した要約の内容も添える）。

### Step 5: 促されたときの即時投稿

「WOL して」「今の進捗を共有して」と言われたら、経過時間を無視して Step 4 を実行する。
状態ファイルが無い（継続モードに入っていない）場合は、その会話で分かっている作業内容から
まとめを作って投稿し、続けて Step 1 の間隔確認をしてよいか尋ねる。

`---` 以下のログが空でも、会話の文脈から前回投稿以降の作業を思い出せるならそれを使ってよい。
本当に何も進捗が無ければ投稿せず、「まだ共有できる差分がありません」と伝える。

### Step 6: 停止

「WOL 止めて」「もう共有しなくていい」と言われたら:

1. `---` 以下に未投稿のログが残っていれば、**最後のまとめを投稿するか確認**する（勝手に投稿しない）。
2. 状態ファイルを削除する（`rm -f "$STATE"`）。
3. 停止した旨と、これまで何回投稿したかを一言伝える。

## 継続についての注意（重要）

Claude は自分の意思で時間が来たら起きる、ということができない。**時間の経過を確認できるのは
ユーザーとのやり取りや作業が動いているときだけ**なので、このスキルの「N 分ごと」は
「N 分経過後、次に作業が一段落したタイミングで投稿する」という意味になる。

- 会話が止まっている間は投稿されない。放置していても投稿されると期待させないこと。
- 厳密なタイマーで動かしたい場合は、ユーザーに `/loop 30m /ai-working-out-loud:wol-slack` の
  ような定期実行の仕組みを使う選択肢を案内する（利用できる環境であれば）。
- 長時間の作業に入る前に投稿間隔が過ぎそうなら、区切りで一度投稿しておく方が親切。

## エラー時の対処

| 症状 | 原因と対処 |
|---|---|
| `必要な環境変数が未設定です: WOL_SLACK_WEBHOOK_URL ...` | Webhook URL 未設定。ユーザーに設定を依頼する。 |
| `webhook への投稿に失敗しました: status=404` | Webhook URL が誤り/失効。再発行を依頼する。 |
| `まとめ本文が空です` | `--summary` に何も渡っていない。ログや文脈からまとめ直す。 |
| `command not found: wol-slack` | 前提条件 2 の手順でバイナリを用意する。 |

投稿に失敗した場合は `last_posted_epoch` を更新せず、ログもクリアしない（次回にまとめて投稿できる）。

## 注意

- 投稿はユーザーの Slack チャンネルに実際に流れる。**連投しない**（間隔より短い間隔で投稿を重ねない）。
- 秘匿情報（トークン、認証情報、顧客データ、未公開の内部情報）を本文に含めない。
- 進捗を**盛らない**。うまくいっていないこと・詰まっていることも、そのまま短く書く方が WOL として価値がある。
- ログの丸写しや、コマンド出力の長い貼り付けは避ける。読み手は数十秒で読める分量を期待している。
